Why bother

発売時の相手は RTX 3060 だった

A770 が出た 2022 年、Intel が比較相手に選んだのは GeForce RTX 3060 でした。それから 4 年、同じカードがソフトウェアのチューニングだけで、現行世代の GeForce RTX 5060 と同じ水準の数字を出しています。ハードウェアは 1 枚も買い足していません。

VRAM 16GB のカードが手に入りにくい今、引き出しで眠っている A770 があるなら、ローカル LLM 用の 1 枚としてもう一度挿してみる価値があります。9B クラスのモデルなら 256K トークンの文脈まで載り、三値の Bonsai 2 なら 27B も動きます。

Memory bandwidth

カタログでは 25% 広い帯域が、実際にはほぼ同じ

文章生成は、1 トークンごとに重みを全部メモリから読む処理なので、速さの上限はメモリの読み出し速度で決まります。A770 の公称帯域は 560 GB/s で GeForce RTX 5060（448 GB/s）より 25% 広いのですが、実際に読める速さは約 434 GB/s（公称の 77%）で、RTX 5060 の 426 GB/s（95%）とほぼ並びます。ハードウェアの優位は、ここでほとんど消えています。

Down to the assembly

どこまで降りたか

GPU のコードは、ソースが正しくても速いとは限りません。Intel のシェーダコンパイラ（IGC）が実際に出力したアセンブリを 1 命令ずつ読み、遅い理由を見つけたところから書き直しています。重い部分は ESIMD（レジスタの割り当てまで自分で決める、アセンブラに近い書き方）で書きました。

プリフィル
アセンブラは不要。行列積は Intel 自身の oneDNN に任せた

4bit / 8bit の重みのまま XMX に流す「重み圧縮 GEMM」が oneDNN に用意されていました。llama.cpp の汎用経路はこれを使わず、毎回 f16 に展開してから掛けていました。

55〜90 TFLOPS 相当 · Llama pp512 1,849 → 3,761
線形アテンション（DeltaNet）
アセンブリを読み、ESIMD でレジスタを手で配置

コンパイラはループを展開すると全ロードを先頭へ寄せ、1 スレッドあたり 2〜9 KB をスタックへ溢れさせていました。そのままでは逐次版より遅かったものを、ESIMD で書き直してスピル 0 にしています。

スピル 9 KB → 0 · Qwen pp512 2,295 → 2,481
生成（デコード）
アセンブリで原因を特定し、XMX の DPAS 命令を ESIMD で直接書いた

アセンブリを読むと、16 バイトのロードが 4 バイトずつに分解されていたり、添字計算が 64bit 整数の模倣命令の連鎖になっていたりしました。量子化 KV キャッシュの Flash Attention は、行列演算命令（DPAS）を直接呼ぶ形で書いています。

FA デコード 2× · 64bit 添字の除去で約 +10% · Bonsai 59 → 141 t/s

どれも「動くが、A770 向けには詰め切られていない」部分でした。汎用のコンパイラ出力や既存の実装は、より新しい GPU や他社の GPU を主な対象にしていて、Alchemist の癖（64bit 整数を持たない、レジスタ 128 本、XMX の幅 8）までは追い込まれていません。そこを埋めるだけで、この差が出ました。

How

何をどうやったか

土台を選ぶVulkan → SYCL
  • 公式 Vulkan は Alchemist の XMX（行列演算ユニット）をほぼ使えず、プリフィルが SYCL の半分以下でした。SYCL（oneAPI）に乗り換え、三値モデルを扱える PrismML フォークを起点にしました。
  • 以降は Intel のシェーダコンパイラ（IGC）が出すアセンブリを読みながら、カーネル単位で書き換えています。
プリフィル行列積
  • 4bit / 8bit の重みを f16 に展開してから掛けていたのをやめ、oneDNN の「重み圧縮 GEMM」で量子化重みのまま XMX に流しました。
  • Q4_0 は推論用に並べ替え済みのメモリをそのまま読み、ニブル順の違いは入力側を並べ替えて吸収。Q4_K は最小値の項を「9 番目のグループ」として同じ行列積に畳み込みました。
  • Llama 2 7B pp512：1,849 → 3,761
線形アテンションGated DeltaNet
  • Qwen3.5 / Bonsai の DeltaNet 層は 1 トークンずつ状態を更新する逐次処理でした。32 トークンごとのチャンク形式（UT/WY 変換）に書き換え、チャンク間の逐次部分だけを ESIMD で手書きしてレジスタ溢れを無くしました。
  • Qwen3.5 9B pp512：2,295 → 2,481
生成（Llama）行列ベクトル積
  • Q4_0 の行列ベクトル積を「1 レーン 1 ブロック・複数行で入力共有」に書き直し、正規化や SwiGLU が次の積用の 8bit 量子化を自分で書く融合を追加。量子化 KV キャッシュの Flash Attention は XMX（DPAS 命令）で実装しました。
  • Llama 2 7B tg128：55.1 → 91.1
生成（三値 Bonsai）1 トークン 16.9 ms → 7.1 ms
  • A770 では使える GPU プロファイラが無かったため、各処理の前に GPU の時計を読む小さなカーネルを差し込んで、1 トークン内の時間配分を可視化するツールを作りました。
  • 最大の原因は 64bit 整数の添字計算でした。A770 はこれをハードウェアで持たず数十命令で模倣するため、4,096 要素の正規化に 12 µs かかっていました。添字を 32bit にするだけで約 1 割速くなりました。
  • 1 トークンに約 130 回あるアダマール回転（重みの前処理）を、1 ワークグループ・12 回同期から 1,024 スレッド・同期 1 回に。直前の残差加算と正規化、アテンションの出力ゲートもこの中に入れました。
  • DeltaNet の出力処理、アテンションの Q/K 正規化 + RoPE + KV キャッシュ書き込み、ゲート計算、同じ入力を読む行列ベクトル積（qkv + z、gate + up + SwiGLU）をそれぞれ 1 カーネルにまとめ、不要なコピーも削除しました。
  • Bonsai 2 9B tg128：59.1（改造前）→ 140.7
Lessons

A770 で分かったこと

公称 560 GB/s、実測は約 434 GB/s

メモリの読み出しは、どう書いても公称値の約 77% で頭打ちでした。GeForce RTX 5060 は同じ測り方で公称の 95% が出ます。文章生成の速さはほぼこの帯域で決まるので、ハードウェアとしていちばん損をしている部分です。ソフトウェアで取り返せたのは、この上限の手前までです。

64bit 整数はソフトウェア

乗算・除算は数十命令に展開されます。小さなカーネルほど添字計算が支配的になるので、オフセットは 32bit で持ちます。

1 ワークグループのカーネルは重くしない

起動回数を 1 つ減らしても、単一ワークグループの処理に仕事を足すと全体は遅くなりました。量子化の同居などは別カーネルの方が速い。

レジスタは 128 本しかない

SIMD16 の float は 1 個で 2 本を使います。ループを展開した SIMT カーネルはすぐ溢れるので、重い部分は ESIMD でレジスタを明示しました。

大きな縮約は 2 段で

1,024 幅の reduce_over_group より、サブグループで足して SLM 経由でもう一度足す方が速い。

キャッシュと起動の損失

L2 に乗った行の読み出しは約 0.8 TB/s が上限。行列ベクトル積は起動ごとに約 9 µs の立ち上がりと末尾の損失があります。

うまくいかなかったこと

三値重みの行列ベクトル積は 6 通り（ESIMD のテーブル展開やベクトル展開を含む）書き直しましたが、どれも既存カーネルより遅く、採用していません。
